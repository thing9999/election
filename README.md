# 협회장 선거 전자투표 시스템

React (Vite) + NestJS + PostgreSQL. 회원명부 기반 1인 1표, 비밀투표.

```
apps/web    유권자 투표 화면      :5173
apps/admin  선거관리위원회 화면    :5174   ← 별도 앱. 다른 호스트에 배포하고 IP 제한
apps/api    API 서버              :4000
packages/ballot-seal   봉인 규격 (브라우저·서버 공유)
```

관리자 화면을 별도 앱으로 둔 이유는 **유권자 번들에 관리자 코드가 섞이지 않게** 하고,
배포 위치와 접근 제어를 따로 걸기 위해서입니다.

## 1. 설계의 핵심 한 가지

**"누가 투표했는가"와 "무엇을 찍었는가"를 물리적으로 분리한다.**

```
Voter 테이블                          Ballot 테이블
├─ memberNoHash                       ├─ id (랜덤 UUID)
├─ phoneHash                          ├─ sealedVote (봉인된 133바이트)
├─ hasVoted  ←── 중복 투표 차단        ├─ castAtHour (시 단위로 뭉갬)
└─ votedAt                            └─ (voterId 컬럼이 없음)

        └────── FK 없음. 조인 불가. ──────┘
```

이게 왜 중요한가: 두 테이블을 이어주는 컬럼이 하나라도 있으면, DB 접근 권한이 있는
사람(개발자·DBA·서버 침입자)이 회원 개개인의 표를 볼 수 있다. 그러면 그건 비밀투표가
아니다. 선거 후 분쟁에서 이 구조 자체가 "볼 수 없었다"는 증거가 된다.

부수적으로 지켜야 할 것들:

| 항목 | 이유 |
|---|---|
| 표를 **브라우저에서** 봉인 (`sealedVote`) | 평문이면 DB·로그·TLS 종단 어디서든 개표 전 중간 집계가 나온다. 서버에서 봉인하면 침입자가 요청 핸들러에서 실시간으로 본다 (3장) |
| `Ballot.castAtHour` 는 시(hour) 단위 | 초 단위 시각이 남으면 접속 로그의 로그인 시각과 대조해 표를 역추적할 수 있다 |
| 감사 로그의 `VOTER` 액션에 `actorRef` 를 넣지 않음 | 같은 이유. "몇 시 몇 분에 누가 투표"가 남으면 안 된다 |
| 투표 확인번호에 후보 정보를 담지 않음 | 자기 표를 증명할 수 있으면 매표(vote buying)가 성립한다 |
| 후보별 득표는 `TALLIED` 전까지 API 자체가 거부 | 중간 집계 노출은 남은 유권자의 선택을 바꾼다. 그것만으로 선거가 무효가 될 수 있다 |
| 회원번호·휴대폰은 HMAC 해시로만 저장 | DB 만 유출되어도 명부를 복원할 수 없어야 한다. pepper 는 DB 밖(KMS)에 둔다 |

## 2. 1인 1표는 이 한 줄이 보장한다

[vote.service.ts](apps/api/src/vote/vote.service.ts) 안:

```sql
UPDATE voter SET has_voted = true WHERE id = ? AND has_voted = false
```

원자적 compare-and-swap이다. 같은 사람의 요청이 동시에 두 개 들어오면 Postgres가 행 잠금을
걸고, 나중 트랜잭션은 커밋된 값으로 `WHERE`를 재평가하므로 0건이 매칭된다 → 두 번째 표는
만들어지지 않는다. 이 UPDATE와 `INSERT INTO ballot`이 한 트랜잭션 안에 있어서, 둘 중 하나만
일어나는 상태가 없다.

서로 다른 유권자는 서로 다른 행이므로 경합이 없다. **1만 명이 같은 순간에 눌러도 잠금
대기가 생기지 않는다.** 이 설계에서 병목은 DB 커넥션 수이지 잠금이 아니다.

## 3. 표는 브라우저에서 봉인한다

익명성을 "연결이 없다"로만 지키면 구멍이 남습니다. 후보 ID가 평문이면
**누가 찍었는지는 몰라도 개표 전 중간 집계는 볼 수 있습니다.**

```sql
SELECT "candidateId", COUNT(*) FROM "Ballot" GROUP BY 1;   -- 이 한 줄이면 끝
```

### 왜 서버가 아니라 브라우저인가

처음에는 서버에서 봉인했는데, 그러면 **봉인의 이유 자체가 무너집니다.**
서버를 뚫은 사람은 개인키를 찾을 필요가 없습니다 — 요청 핸들러에 한 줄만 붙이면
들어오는 표를 실시간으로 다 봅니다. 평문이 지나는 곳이 이만큼 됩니다:

| 지점 | 서버 봉인 | 브라우저 봉인 |
|---|---|---|
| TLS 종단 (ALB·CloudFront) | 평문 노출 | 133바이트만 통과 |
| 요청 로그·APM·에러 트레이스 | 평문이 남을 수 있음 | 남을 것이 없음 |
| 서버 메모리·힙덤프 | 평문 존재 | 평문 없음 |
| 침입자의 실시간 관전 | **가능** | 불가능 |

그래서 봉인을 브라우저로 옮겼습니다. 서버는 평문 `candidateId`를 **받지 않습니다** —
보내면 400입니다.

```
봉인된 표 (133바이트, 항상 동일)
┌────────────────────┬─────────┬───────────────────┐
│ 일회용 공개키 65   │ nonce 12│ 암호문+태그 56    │
└────────────────────┴─────────┴───────────────────┘
```

ECIES 구조입니다 — 표마다 **일회용 키쌍**을 새로 만들어 선거 공개키와 P-256 ECDH 하고,
HKDF로 뽑은 키로 AES-256-GCM 암호화합니다.

| 설계 | 이유 |
|---|---|
| 곡선은 P-256 | X25519가 더 현대적이지만 브라우저 Web Crypto 지원이 최근이라 구형 기기에서 안 됩니다. 유권자 연령대를 생각하면 호환성이 우선이고, **암호 라이브러리를 하나도 안 실어도 됩니다** |
| 표마다 일회용 키 | 고정 키면 같은 후보 → 같은 암호문. 암호문을 묶어 세는 것만으로 집계가 나옵니다 |
| 평문을 40바이트로 패딩 | 길이가 다르면 암호문 크기만 재고도 기권 여부가 드러납니다 |
| HKDF info에 선거 공개키 | 다른 선거의 표를 옮겨 붙이지 못하게 합니다 |
| GCM 인증 태그 | 저장 후 한 바이트만 바뀌어도 개봉이 실패합니다 |
| **개인키를 DB에 두지 않음** | 담을 컬럼 자체가 없습니다. 선거 생성 시 한 번 출력되고 서버에서 사라집니다 |

### 봉인 코드는 일부러 공개합니다

[packages/ballot-seal/seal.ts](packages/ballot-seal/seal.ts)가 유권자 브라우저에서
실제로 도는 유일한 암호 코드입니다. 60줄 남짓이고, 라이브러리 없이, 난독화 없이 썼습니다.

WASM 같은 걸로 감추는 건 **역효과입니다.** 이유가 셋입니다:

1. WASM은 `wasm2wat` 한 번이면 읽힙니다. Rust 빌드는 심볼과 panic 문자열이 그대로 남습니다
2. 어차피 JS 경계를 지납니다 — `DOM → WASM → fetch`. 페이지를 바꿀 수 있는 공격자는 양쪽 끝을 후킹하면 됩니다
3. **막으려는 건 "읽기"가 아니라 "바꿔치기"입니다.** 읽기 어렵게 해도 바꾸기는 똑같이 쉽습니다

무엇보다 선거에서는 후보 캠프·참관인·기자가 투표 페이지가 뭘 하는지 읽을 수 있어야 합니다.
"우리 모듈은 바이너리라 아무도 못 읽습니다"는 분쟁에서 방어가 아니라 공격받을 지점입니다.
Helios나 Belenios가 클라이언트 소스를 의도적으로 공개하는 이유가 이겁니다.

> Kerckhoffs의 원칙 — 안전성은 알고리즘의 비밀이 아니라 **키의 비밀**에만 의존해야 합니다.

### 대신 치른 비용 — 서버가 후보를 검증할 수 없다

봉인된 표는 서버가 열 수 없으므로 **"이 선거에 있는 후보인가"를 투표 시점에 확인할 방법이
없습니다.** 서버가 할 수 있는 건 길이가 133바이트인지 보는 것뿐입니다.

조작된 클라이언트가 존재하지 않는 후보를 봉인해 보낼 수 있고, 그건 개표 때 드러납니다.
**그때 개표를 중단하면 유권자 한 명이 표 하나로 선거 전체를 막을 수 있습니다.**
그래서 무효표로 세고 계속하되, 개수를 반드시 남기고 결과에 표시합니다.
조용히 버리지 않는 이유는 그 자체가 조작 수단이 되기 때문입니다.

### 이게 막는 것과 못 막는 것

**막습니다:** TLS 종단·로그·서버 메모리 노출, 침입자의 실시간 중간 집계 열람,
DB·백업 유출 시 표 내용 노출, 저장 후 변조.

**못 막습니다:** 그 JavaScript를 내려주는 게 서버입니다. 뚫린 서버는 조작된 코드를 보내
선택을 빼돌리거나 다른 후보로 봉인시킬 수 있습니다. 브라우저 투표의 근본 한계이고
Helios도 여기서 멈춥니다. **수동적 도청(쉽고 조용함)을 능동적 코드 교체(어렵고 흔적이
남음)로 바꾸는 것**이지, 서버를 신뢰 대상에서 빼는 게 아닙니다.

이에 대한 방어는 난독화가 아니라 **대조 가능성**입니다 — 투표 클라이언트의 빌드 해시를
사전 공고하고, 후보 캠프·참관인이 선거 기간 중 직접 받아서 대조할 수 있게 하세요 (11장).

개표 시점에는 서버 메모리에서 개별 표가 복호화됩니다. 이때도 "누가 찍었는지"는 알 수
없지만(Voter–Ballot 연결이 없으므로) 개별 표는 잠시 평문이 됩니다. 없애려면
**동형암호**(exponential ElGamal)로 암호문 상태에서 합산해야 합니다.

### 실제로 확인한 것

`npm run crypto:check --workspace=apps/api` — 브라우저 봉인 모듈을 그대로 불러와
서버 개봉과 맞물리는지 12개 항목을 검증합니다(DB 불필요). 사본을 두지 않으므로
둘이 갈라질 수 없습니다.

DB를 통째로 읽었을 때:

```
저장된 표:  043bb9ea92fb3c6280eff4729608b526…  (133B)
암호문으로 GROUP BY → 최다 그룹 크기 1     ← 집계가 안 나온다
Election 컬럼: id, title, …, ballotPublicKey  ← 공개키뿐, 개인키 컬럼 없음
```

성능: **봉인 1,351 표/초**(유권자 기기 1대 기준, 실제로는 각자 한 번씩) ·
**개봉 5,141 표/초** — 1만 표 개표에 약 2초.

## 4. 로그인은 휴대폰번호만 받는다

회원번호는 **인증에 아무것도 더하지 못합니다.** 본인 확인은 "이 번호로 온 문자를 받았다"가
전부이고, 회원번호는 회원증과 명부에 적혀 있어 비밀이 아닙니다. 반면 못 외우는 회원이
많아 투표율만 깎고 콜센터 부담만 늘립니다. 그래서 로그인 화면에서 뺐습니다.

```
휴대폰번호 + 생년월일 → 인증번호 6자리 → 투표
```

생년월일을 함께 받는 이유는 아래 "문자를 받았다고 본인은 아니다"에 있습니다.

명부 CSV에는 회원번호가 그대로 들어갑니다 — 명부 관리와 대조에 필요하기 때문입니다.
**로그인에서만 빠집니다.**

### 문자를 받았다고 본인인 것은 아니다

폰을 가지고 있다는 것과 본인이라는 것은 다릅니다. 실제로 뚫리는 경우가 있습니다:

- 명부의 번호가 낡아 **지금은 남의 번호** → 그 사람이 코드를 받고 투표
- 가족·병원 직원이 폰을 들고 대리투표

그래서 **생년월일**을 함께 받습니다. 회원번호와 달리 누구나 외우고 있어 투표율을 깎지
않으면서, 폰만 손에 넣은 사람은 통과하지 못합니다. 구분자를 어떻게 넣든(`1975-03-14`,
`1975.3.14`, `19750314`) 받아줍니다 — 고령 유권자가 형식 때문에 막히면 안 됩니다.

생년월일이 틀리면 **문자를 아예 보내지 않습니다.** SMS 비용도 아끼고, 남의 번호로
인증문자를 반복 발송해 괴롭히는 것도 막습니다.

수단별로 어디까지 막히는지는 분명히 해둡니다:

| 방법 | 막는 것 | **못 막는 것** |
|---|---|---|
| SMS만 | 명부에 없는 사람 | 폰을 가진 누구나 |
| **+ 생년월일 (지금)** | 폰을 줍거나 훔친 사람, 명부 번호가 낡아 남의 번호가 된 경우 | **가족·직원 대리투표** |
| 본인확인 서비스 | 위 전부 + 폰 명의가 본인이 아닌 경우 | 본인이 옆에서 시켜서 하는 경우 |

**가족 대리투표는 생년월일로 못 막습니다** — 가족이면 아는 값이니까요. 진짜 답은
본인확인 서비스(PASS·NICE·KCB·간편인증)입니다. 통신사 등록 명의와 대조하므로
"이 폰이 그 회원 본인 명의인가"까지 확인됩니다. 계약이 필요해 아직 안 붙였지만,
들어올 자리를 [identity-verification.ts](apps/api/src/auth/identity-verification.ts)에
인터페이스와 함께 남겨뒀습니다. 협회장 선거처럼 법적 효력이 있는 선거라면
**이건 선택이 아니라 필수에 가깝습니다.**

### 대신 반드시 필요한 것 — 회원마다 고유한 번호

휴대폰이 로그인 키가 되므로 **한 번호에 두 회원이 걸리면 안 됩니다.** 그 폰을 쥔 사람이
두 명 몫을 투표할 수 있기 때문입니다. 개원의 부부나 병원 대표번호를 적은 경우 실제로
생길 수 있는 일입니다.

이건 회원번호를 받든 안 받든 필요한 조건입니다 — 회원번호는 비밀이 아니라서 방어가
되지 않습니다. 그래서 두 겹으로 막습니다:

- `Voter.@@unique([electionId, phoneHash])` — DB 차원
- 명부 업로드 시 중복을 찾아 **거부하고, 몇 행끼리 겹쳤는지 알려줍니다**

```
같은 휴대폰번호가 여러 회원에게 등록되어 있습니다 (2건).
휴대폰은 로그인 수단이라 회원마다 달라야 합니다 — 겹치면 그 번호를 가진 사람이
두 명 몫을 투표할 수 있습니다. [2행 · 3행 (···0001), 7행 · 9행 (···4412)]
```

### 이름은 인증 통과 후에 알려준다

인증번호를 넣기 **전에** 이름을 보여주면 "이 번호가 명부에 있고 누구 것인지"가 그대로
새어나갑니다. 그래서 요청 단계에서는 마스킹된 뒷자리만 돌려주고, 인증을 통과한 뒤에야
투표 화면에서 `테*0001 님으로 확인되었습니다`로 보여줍니다 — 유권자가 본인이 맞게
인식됐는지 확인할 수 있습니다.

미등록 번호는 어떤 번호든 **똑같은 응답**을 받습니다. 응답이 다르면 명부를 긁어낼 수 있습니다.

## 5. 실행

Docker 없이 로컬에서 전부 돌아갑니다. `node_modules` 안의 PostgreSQL 바이너리를 그대로
띄우므로 시스템에는 아무것도 설치되지 않습니다.

```bash
npm install
cp apps/api/.env.example apps/api/.env
# VOTER_ID_PEPPER / JWT_SECRET 생성해서 .env 에 넣기

# 터미널 1 — 로컬 Postgres (127.0.0.1:5433, 데이터는 apps/api/.pgdata)
```

`Ctrl+C` 한 번이면 같이 뜬 프로세스가 전부 정리됩니다.

> Windows 에서 `A & B` 는 백그라운드가 아니라 순차 실행이라 두 번째가 영영 안 뜹니다.
> 그래서 `concurrently` 를 씁니다 — 로그에 `[api]` `[admin]` 접두어가 붙어 어느 쪽

검증은 `npm run check` 하나로 전부 돌아갑니다 (봉인 모듈 → E2E → 관리자 흐름).
API 서버가 떠 있어야 하고, 단일 IP 에서 몰아치므로 스로틀을 풀고 띄워야 합니다:

```bash
THROTTLE_OTP_REQUEST=5000 THROTTLE_ADMIN_LOGIN=500 npm run start:api
```

데이터를 갈아엎으려면 `npm run db:local --workspace=apps/api -- --reset`.

운영 배포 시에는 [Neon](https://neon.tech)이나 RDS 같은 관리형 Postgres를 씁니다.
그때는 연결 문자열이 **두 개** 필요합니다 — 런타임용 풀링(`-pooler`)과 마이그레이션용
직접 연결. Prisma는 PgBouncer를 통해 DDL을 실행하면 실패하므로
[schema.prisma](apps/api/prisma/schema.prisma)에 `directUrl`을 걸어뒀습니다.

`SMS_PROVIDER=mock` 이면 인증번호가 API 서버 콘솔과 `apps/api/.dev-otp.json` 에 남으므로,
문자 계약 전에도 전 과정을 자동 테스트할 수 있습니다.

## 6. 실측치

로컬 1대(개발용 노트북, API·DB 같은 머신, 단일 노드)에서 유권자 1만 명 명부로 측정:

| 구간 | 처리량 | 지연 |
|---|---|---|
| 인증 (OTP 발송+검증) | **42.3 건/초** | — |
| 투표 (500건 동시 발사) | **546 표/초** | p50 716ms · p99 869ms |

500건 동시 투표에서 성공 500 · 중복 0 · 유실 0, `hasVoted` 수와 실제 표 수 일치.
**투표 경로는 병목이 아닙니다.** 인증이 투표보다 13배 느립니다.

인증이 느린 이유는 argon2 해싱이고, 이건 의도된 비용입니다. 다만 라이브러리 기본값
(64MiB·t=3·p=4)은 수년간 유지되는 비밀번호 기준이라 3분 만료 OTP에는 과합니다.
OWASP argon2id 최소 권장치(19MiB·t=2·p=1)로 낮춰 **13.8 → 42.3건/초**로 올렸습니다
([auth.service.ts](apps/api/src/auth/auth.service.ts) 상단, 환경변수로 조정 가능).

1만 명 기준 용량 계산:

- 42.3건/초 → 1만 명 인증에 순수 CPU 시간 약 **4분**
- 최악을 가정해 2,000명이 마감 직전 5분에 몰려도 **6.7건/초** — 여유 6배
- API는 상태가 없으므로 부족하면 인스턴스만 늘리면 됩니다

측정 재현: `VOTER_COUNT=10000 npm run seed --workspace=apps/api` 후
`LOAD_N=500 npm run load --workspace=apps/api`.

> 주의: 단일 노트북 수치이고 네트워크 지연이 없습니다. 실제 배포 구성에서 반드시
> 다시 재세요. 특히 SMS 게이트웨이 응답 시간이 여기 안 들어가 있습니다.

## 7. 관리자 인증

선관위 계정 하나가 뚫리면 선거 전체가 무너집니다. 그래서 비밀번호만으로는 아무것도 할 수
없게 만들었습니다.

```
아이디 + 비밀번호  ──▶  pendingToken (5분, 아무 권한 없음)
                            │
                        TOTP 6자리
                            │
                            ▼
                      관리자 토큰 (30분)
```

`pendingToken`으로는 관리자 API가 전부 401입니다. TOTP를 통과해야만 실제 토큰이 나옵니다.

| 방어 | 구현 |
|---|---|
| 계정 목록 유출 | 없는 계정과 틀린 비밀번호가 **같은 응답**. 없는 계정도 argon2를 한 번 돌려 응답 시간까지 맞춤 |
| 무차별 대입 | 5회 실패 → 30분 잠금. 비밀번호와 TOTP가 같은 카운터를 공유 |
| 코드 훔쳐보기 | 이미 쓴 시간 슬롯의 TOTP는 유효시간이 남아도 거부 (`afterTimeStep`) |
| 시계 오차 | 과거 방향 30초만 허용. 미래 방향은 열지 않음 |
| 2차 인증 갈아끼우기 | 등록된 계정은 재등록 불가 — 세션을 뺏겨도 공격자 기기로 옮길 수 없음 |
| 퇴임한 위원 | 매 요청마다 DB에서 `disabledAt` 확인. 남은 토큰이 만료까지 도는 걸 막음 |
| 역할 | 기본이 거부. 참관인(AUDITOR)에게 열어줄 조회 API에만 `@Roles` 명시 |

**관리자 계정을 만드는 HTTP 엔드포인트는 일부러 없습니다.** 서버 접근 권한이 있는
사람만 CLI로 만들 수 있습니다:

```bash
npm run admin:create --workspace=apps/api -- --id kim --name 김위원 --role COMMISSIONER
npm run admin:create --workspace=apps/api -- --id lee --name 이참관 --role AUDITOR
```

임시 비밀번호가 출력되고 다시 볼 수 없습니다. 비밀번호를 인자로 받지 않는 것은
셸 히스토리와 프로세스 목록에 남기 때문입니다.

### 개표 2인 승인 (dual control)

개표는 선관위원 **2명이 각자** 승인해야 실행됩니다. 1차 승인은 기록만 남기고 결과를
열지 않습니다.

```
위원A 승인 ─▶ 승인 1/2, 결과 여전히 비공개
위원B 승인 ─▶ 승인 2/2, 개표 실행 → TALLIED
```

같은 사람이 두 번 눌러 정족수를 채울 수 없고(`@@unique([electionId, adminId])`),
참관인은 승인할 수 없으며, 무결성 점검이 깨져 있으면 승인 자체를 받지 않습니다.
정족수는 `TALLY_QUORUM`으로 바꿀 수 있지만 1로 낮추지 마세요 — 계정 하나가 뚫렸을 때
그 사람이 임의 시점에 개표해 결과를 먼저 보는 걸 막는 게 이 장치의 목적입니다.

## 8. 관리자 화면

`apps/admin` — 선관위 전용 별도 앱입니다. `npm run dev --workspace=apps/admin` (`:5174`).

| 화면 | 하는 일 |
|---|---|
| 로그인 | 비밀번호 → TOTP. 최초 로그인이면 QR로 2차 인증 등록 |
| 선거 목록 | 상태·선거인 수·투표율 한눈에 |
| 새 선거 | 선거 정보 + 후보 등록. **생성 직후 개표키를 한 번만 보여줍니다** |
| 선거 상세 | 명부 등록 → 개시 → 마감 → 개표 승인 → 결과 |

설계에서 신경 쓴 것들:

- **토큰을 `localStorage` 에 두지 않습니다.** XSS 한 번으로 선거 전체가 넘어가고,
  공용 PC 에서 브라우저를 닫아도 남습니다. 메모리에만 두므로 새로고침하면 다시
  로그인해야 하지만 선관위 화면은 그게 맞습니다.
- **개표키 화면은 건너뛸 수 없습니다.** "안전한 곳에 보관했다"를 체크해야 닫힙니다.
  서버에 저장하지 않으므로 놓치면 개표가 영구히 불가능합니다.
- **후보별 득표는 개표 전까지 이 화면에도 안 나옵니다.** 선관위 화면이라고 예외를
  두면 그 화면이 곧 유출 경로가 됩니다. 진행 중에 보이는 건 투표율뿐입니다.
- **개표키는 승인할 때마다 다시 입력**합니다. 세션에도 담지 않습니다.
- 되돌릴 수 없는 행동(개시·마감)은 현재 수치를 보여주는 확인 창을 거칩니다.
- 참관인(AUDITOR)은 모든 수치를 보지만 버튼이 아예 나오지 않습니다.

`npm run admin:check --workspace=apps/api` 로 이 화면이 쓰는 API 경로를 전부
검증합니다 (24개 항목: 권한 분리, 기호 중복 거부, 개시 후 명부·후보 변경 거부,
개인키가 DB 에 없음, 2인 승인 개표).

## 9. 결과 무결성 — 뚫려도 드러나게

봉인은 **개표 전에 표를 못 읽게** 합니다. 그런데 DB **쓰기** 권한이 있으면 얘기가 다릅니다:

| 공격 | 봉인만으로 막히나 |
|---|---|
| 개표 후 `TallyResult` 숫자를 고침 | ✗ |
| `Ballot` 행을 넣거나 지움 | ✗ (`Voter.hasVoted`도 같이 고치면 표 수 대조도 통과) |
| 감사 로그에서 흔적 삭제 | ✗ — 같은 DB |
| 명부에 가짜 유권자 추가 | ✗ |

전부 **한 DB 안에서 완결되므로** 내부 정합성 검사로는 잡히지 않습니다.

### 표마다 체인을 걸면 안 됩니다

흔한 실수입니다. 표마다 이전 해시를 물리면 **모든 투표가 한 줄로 직렬화**됩니다.
546표/초가 나오는 건 서로 다른 유권자가 서로 다른 행을 건드려 경합이 없어서인데,
체인 머리를 잠그는 순간 그게 사라집니다.

대신 **머클 트리 체크포인트**를 씁니다 — 투표 경로는 손대지 않고, 단계마다 그 시점의
상태를 해시로 굳혀 체크포인트끼리 연결합니다. Certificate Transparency와 같은 구조입니다.

```
개시              투표 중              마감            개표
 │                  │                    │              │
 ▼                  ▼                    ▼              ▼
CP#1            CP#2 · CP#3 ···        CP#n          CP#n+1
명부 해시        표 머클 루트           최종 루트      결과 해시
 └────── 각 체크포인트가 이전 것의 해시를 품는다 ──────┘
                        │
                        ▼
            외부 고정 (참관인 · TSA · 블록체인)
```

`ROSTER_SEALED`는 개시 시점의 명부를 굳힙니다. 이게 있어야 **투표 중 가짜 유권자
추가**가 드러납니다.

### 실제로 잡히는지 확인했습니다

`npm run tamper:check --workspace=apps/api` — DB를 직접 고쳐 공격자를 흉내내고,
검증이 **실패로 뒤집히는지**를 봅니다 (16개 항목):

```
1. 표를 몰래 넣으면      ✓ 탐지 (확정 당시 10장 → 현재 11장)
2. 표를 몰래 지우면      ✓ 탐지
3. 표를 바꿔치기하면     ✓ 탐지 (개수는 그대로인데도)
4. 가짜 유권자를 넣으면  ✓ 탐지 (명부가 개시 당시와 다릅니다)
5. 체크포인트를 고치면   ✓ 탐지 (자기 해시와 안 맞음)
6. 체크포인트를 지우면   ✓ 탐지 (사슬이 끊김)
7. 득표수를 고치면       ✓ 탐지
```

### 블록체인은 저장소가 아니라 공증인입니다

해시 사슬만으로는 **부족합니다.** DB를 통째로 쥔 공격자는 표를 고친 뒤 체크포인트도
처음부터 다시 계산해 끼워넣으면 그만입니다. 사슬은 "내부적으로 앞뒤가 맞는가"만
보장합니다. 검증 스크립트의 8번 항목이 정확히 이걸 보여줍니다 — **사슬을 통째로
다시 만들면 내부 검증은 통과합니다.**

그래서 사슬의 머리를 **협회가 나중에 바꿀 수 없는 곳**에 남깁니다.

| 대상 | 성격 |
|---|---|
| `OBSERVERS` | 참관인·후보 캠프에 해시 발송. 무료, 즉시, **사람이 증인**. 기술적으로 가장 약해 보이지만 분쟁에서 가장 강합니다 — 이해관계가 다른 여러 사람이 같은 값을 들고 있으니까요 |
| `FILE` | append-only 외부 저장소(S3 Object Lock 등). 같은 DB 밖에 두는 게 핵심 |
| `TSA` | RFC 3161 공인 타임스탬프. 법적 효력, 저렴 |
| `BLOCKCHAIN` | 퍼블릭 체인에 **해시만** 기록. 특정 기관을 안 믿어도 되고 영구 검증 가능 |

`ANCHOR_TARGETS`로 지정하며, **성격이 다른 둘 이상**을 쓰세요. 한 곳만 쓰면 그곳이
단일 실패 지점이 됩니다.

블록체인 연동은 [anchor.ts](apps/api/src/integrity/anchor.ts)에 인터페이스와 함께
붙일 때 주의할 점을 적어뒀습니다. 요점만:

- **스마트 컨트랙트는 필요 없습니다.** 트랜잭션 데이터 필드에 해시를 넣으면 충분하고,
  컨트랙트를 두면 그 코드가 새 공격 표면이 됩니다
- **지갑 개인키가 새 문제로 생깁니다.** 이 키가 털리면 가짜 고정을 만들 수 있으니
  **개표키와 같은 수준으로** 취급하세요
- 올라가는 건 해시뿐이라 표 내용도 명부도 노출되지 않고, 선거당 몇 건이라 수수료도 무의미한 수준입니다

### 검증은 누구나 할 수 있어야 합니다

사슬은 **로그인 없이** 공개됩니다. 관리자만 볼 수 있으면 "협회가 스스로를 검증했다"가
되어 아무 의미가 없습니다.

```
GET /api/elections/:id/integrity/chain    사슬 전체 + 고정 기록
GET /api/elections/:id/integrity/verify   재계산 대조 결과
```

나가는 값은 전부 해시라 표도 명부도 복원되지 않습니다.

### 이게 하는 일과 못 하는 일

**합니다:** 조작을 **탐지**합니다. 그리고 외부 고정이 있으면 협회 스스로도 되돌릴 수 없습니다.

**못 합니다:**
- 조작을 **막지는** 못합니다. 드러나게 할 뿐입니다
- **아무도 대조하지 않으면 무의미합니다.** 참관인이 받은 해시를 실제로 맞춰봐야 합니다
- 시스템이 뚫린 뒤 만들어진 데이터를 고정하면 **조작된 상태가 영구 보존**될 뿐입니다.
  고정 이전 단계(명부·인증·봉인)가 먼저 맞아야 합니다
- "시스템이 기록한 것"을 증명할 뿐, "유권자가 의도한 것"은 증명하지 못합니다

## 10. 선거 운영 순서

```
DRAFT ──명부 업로드, 후보 등록──> OPEN ──투표──> CLOSED ──무결성 점검──> TALLIED
```

되돌아가는 전이는 API에 없습니다. 개표를 되돌릴 수 있으면 결과를 신뢰할 수 없습니다.

| 단계 | 엔드포인트 |
|---|---|
| 명부 업로드 (CSV: `memberNo,name,phone,birthDate` — 휴대폰 중복 시 거부) | `POST /api/admin/elections/:id/roster` |
| 투표 개시 | `POST /api/admin/elections/:id/open` |
| 투표 마감 | `POST /api/admin/elections/:id/close` |
| 무결성 점검 | `GET  /api/admin/elections/:id/integrity` |
| 개표 승인 (2인 + 개표키) | `POST /api/admin/elections/:id/tally` — body 에 `privateKey` |
| 개표 승인 현황 | `GET  /api/admin/elections/:id/tally` |

**개표 전 무결성 점검을 반드시 돌리세요.** "투표했다고 표시된 사람 수"와 "실제 표 수"가
다르면 어딘가 잘못된 것이고, 그대로 개표하면 안 됩니다.

명부는 `DRAFT` 상태에서만 등록됩니다. 투표 시작 후 명부가 바뀌면 그 선거는 결과를 신뢰할
수 없기 때문입니다.

**운영 수준**

   막으려면 통신사 명의 대조가 필요합니다. 4장과

5e. **투표 클라이언트 빌드 해시 공고** — 뚫린 서버가 조작된 JS를 내려보내는 건 막을 수
   없지만, 대조는 가능하게 만들 수 있습니다. 빌드 해시를 선거 전에 후보 캠프·참관인에게

   3명이 모여야 복원되는 구조로 올리세요.
